# Hosted Edge verification benchmark

Question: can one Supabase Edge Function download and verify a publication with
50,000,000 bytes of listed file content? MB here is decimal, not MiB. Manifest,
signature, and ZIP headers add to that payload; the measured ZIP size is reported.

**Reliability follow-up:** [1,000 attempts with 20 distinct 1,000-file bundles](soak/results/2026-11-06/REPORT.md).
All 500 sequential requests passed. Concurrent requests exposed the handler's
per-worker busy guard: 118 of 500 concurrent attempts returned HTTP 429; the rest
passed. There were no observed verifier or platform resource-limit failures.

**Updated experiment:** [complete bundle checks and URL submissions](full/results/2026-11-06/REPORT.md)
include the missing metadata, Unicode, and timestamp checks. The initial
1,000-file recommendation held; the 5,000-file stress case hit a CPU limit.
The partial benchmark below is retained for comparison.

[Hosted results, 2026-11-06](results/2026-11-06/REPORT.md): all 31 requests behaved
as expected; median verification took 191–712 ms for the 50 MB fixtures.

This is a benchmark of the proposed `sci-publication/0.18` verification workload.
It does not replace the repository's current Python verifier. The draft is still
being edited on `docs/sci-spec`; this experiment changes neither format nor service.

## What is measured

Fresh synthetic Ed25519 publications are generated by Python's `cryptography`
and checked by TypeScript using WebCrypto, plus pinned `@noble/curves` for strict
nonidentity prime-subgroup point checks. Each request downloads the actual bytes
from temporary private Supabase Storage objects, then verifies:

- Exact manifest SHA-256, duplicate-free JSON, fields, integer sizes, and paths.
- Ed25519 signature, canonical public key encoding, subgroup checks, and scalar bound.
- Every listed file's size and SHA-256, plus every ZIP entry's CRC-32.
- Stored ZIP layout, order, local/central consistency, attributes, offsets, and end record.
- Basic metadata and UTF-8 README validation.

**This is not complete draft conformance.** Full metadata schemas, pinned Unicode
18 character tables, optional timestamp verification, affiliation checks,
revocation lookup, database writes, and moderation are excluded. A successful run
is performance evidence for this workload, not approval of a production verifier.

Cases: 1 MB baseline; 50 MB with 1, 1,000, or 5,000 supporting files; 50 MB with a
1 MiB whitespace-padded manifest; a late bad SHA-256 with a correct ZIP CRC; bad
signature; duplicate JSON key; conflicting central name; trailing bytes; oversized
manifest. Valid cases run five times; negative cases once. This is a sequential
benchmark, not a concurrency/load test. The service would need separate limits for
file count, manifest bytes, total content, and concurrent work.

The implementation buffers one complete bounded ZIP and hashes file views in
sequence. It is not a streaming parser. Upload/download objects are split into
8 MB parts to avoid relying on a project-wide storage upload limit. This adds
multiple HTTP requests; it is not a measurement of R2, GitHub, or loose-file latency.

Results distinguish download wall time, verification wall time, and sampled memory.
**Wall time is not CPU time.** Memory samples are not a guaranteed peak and runtime
RSS may describe a wider process. Where available, separately saved function-scoped
runtime logs provide platform CPU/memory/shutdown evidence. Limits must be evaluated
against hosted results, never local-machine timings.

## Run locally

```sh
python -m pip install cryptography==46.0.3 requests==2.32.5
python benchmarks/edge/generate.py /tmp/sci-edge-fixtures
deno check benchmarks/edge/index.ts benchmarks/edge/check.ts
deno run --allow-read benchmarks/edge/check.ts /tmp/sci-edge-fixtures
```

Use `--small` with the generator for a quicker behavior check; these smaller
fixtures are not the 50 MB performance experiment.

## Run on Supabase

The branch-only `edge-verification-benchmark` workflow uses the repository secret
`SCI_EDGE_BENCH_SUPABASE_TOKEN` (falling back to `SUPABASE_ACCESS_TOKEN`) and variable
`SUPABASE_PROJECT_REF`. It checks function deployment access before uploading
fixtures. It creates one
uniquely named `sci-bench-*` private bucket and function, and removes them in a
`finally` block. No existing function, database table, publication, project setting,
or project secret is changed. The function requires a fresh random per-run token
in addition to gateway JWT verification; only its SHA-256 is embedded in the
temporary deployment. It accepts only generated fixture names,
not arbitrary URLs or uploaded data. Secrets are not stored in artifacts.

The benchmark token needs Edge Functions read/write and log read permissions.
The existing deployment token is passed separately as `SUPABASE_KEY_READ_TOKEN`
only for reading the existing project API key; the new token needs no API-key
secret permission. An enabled existing legacy service-role
key is needed for this harness; it does not enable or rotate keys. Generated
publication keys are disposable and never reused as publisher credentials.

With those environment variables set, the equivalent manual run is:

```sh
python benchmarks/edge/run.py /tmp/sci-edge-fixtures /tmp/sci-edge-results
```

Results and cleanup status are uploaded as `edge-verification-results`. If a CI
runner is forcibly cancelled, use the unique name printed in its log to remove
that benchmark function and bucket. Do not delete any other project resource.

The run uses temporary storage and network traffic and counts toward normal
Supabase quotas. It creates no paid project or compute upgrade.
